# 外接大脑三层硬件总体架构与实施路线

**版本：** V1.0  
**日期：** 2026-10-10  
**适用范围：** 固定式中枢、随身交互设备、智能外设及传统设备智能化模块

## 1. 产品总定义

本项目由三类硬件组成，不把所有功能堆在一个设备里：

```text
随身设备
  = 耳朵、嘴巴、按键和移动交互终端

固定式中枢
  = 大脑、记忆、智能体、任务调度和设备管理中心

智能外设
  = 手、感官和确定性执行器
```

完整链路：

```text
用户说话或输入内容
        ↓
随身设备采集并上传
        ↓
固定式中枢完成语音识别、理解和任务拆解
        ↓
中枢检查设备能力、权限和安全策略
        ↓
通过 MQTT / HTTP / 其他适配协议下发动作命令
        ↓
智能外设执行动作并回传状态
        ↓
固定式中枢组织执行结果
        ↓
随身设备播报或显示回复
```

当前项目已经完成了“本地中枢软件 + 真实录音豆”的第一阶段验证。Mac 上位机后续定位为开发调试工具、设备管理后台和可视化控制台，不作为最终随身设备或固定式中枢产品本体。

## 2. 最先做什么

### 2.1 最先确定：三层设备之间的接口和职责

第一步不是直接画 PCB，而是冻结以下内容：

1. 随身设备如何把文字、语音和会话信息传给固定式中枢；
2. 固定式中枢如何返回识别结果、处理中状态和最终回复；
3. 固定式中枢如何把自然语言整理为结构化设备命令；
4. 智能外设如何接收命令、执行动作和反馈结果；
5. 前一个命令未完成时，后一个命令如何排队、替换、取消或拒绝；
6. 设备离线、网络中断、模型失败和硬件异常如何处理。

接口未冻结前，不开始同时设计三块正式生产板，否则后续改协议会导致硬件、固件和上层软件一起返工。

### 2.2 最先买什么：固定式中枢的计算平台

固定式中枢是否能部署目标模型，取决于模型大小、量化方式、内存、推理速度、散热和功耗。因此第一版不直接自研主板，先购买成熟的 Linux 计算平台或 AI 开发板进行验证。

第一版固定式中枢采用：

```text
成熟 Linux 计算平台
        +
现有 HubService / SQLite / MQTT
        +
语音识别、模型推理、语音合成适配层
```

先用真实模型和真实语音链路测出算力、内存、存储、温度和功耗，再决定后续是：

- 继续使用现成小主机；
- 购买计算模块并设计自研中枢底板；
- 设计带 AI 加速器的专用中枢硬件。

这样可以避免在模型尚未确定前，凭感觉设计一块可能算力不足或功耗过高的中枢主板。

### 2.3 最先打样什么：随身设备交互原型

现有项目已经有真实智能外设录音豆，但还缺少最终产品形态的语音入口。因此在固定中枢使用现成计算平台的同时，第一块真正需要打样的自研硬件建议是随身设备的 EVT 原型。

首版先做“按键说话”，不先做复杂的本地唤醒词。这样可以尽快验证：

```text
真实用户说话
  → 随身设备上传音频
  → 固定式中枢识别并理解
  → 控制真实录音豆
  → 随身设备播报结果
```

## 3. 三类硬件的职责边界

### 3.1 随身设备

### 产品职责

随身设备只负责和用户交互，不保存完整设备数据库，也不承担全局命令调度。

### 必要功能

- 麦克风，采集用户语音；
- 音频编码和上传；
- 扬声器，播放智能体回复；
- Wi-Fi，连接固定式中枢；
- BLE，用于配网、近距离配置或维护；
- 按键或触摸，用于唤醒、按住说话和取消任务；
- USB-C 充电；
- 锂电池充电、放电和保护；
- 电量检测和低电量提示；
- 睡眠、唤醒和低功耗管理；
- 设备身份、配网和 OTA 升级；
- 网络中断和中枢不可用时的明确提示。

### 首版硬件框图

```text
联网主控 / 无线模组
    ├── 数字麦克风或麦克风阵列
    ├── 音频接口 / 编解码
    ├── 功放
    ├── 扬声器
    ├── 按键 / 触摸
    ├── 状态灯或小屏幕
    ├── USB-C 接口
    ├── 充电与电源路径管理
    ├── 电池保护
    └── 电量计
```

### 首版不承担的功能

- 不在设备本地运行完整大模型；
- 不直接控制所有智能外设；
- 不保存完整用户和设备数据库；
- 不决定危险设备的最终安全动作；
- 不在断网时伪造命令已经完成。

### 3.2 固定式中枢

### 产品职责

固定式中枢负责接收内容、运行智能体、维护记忆、调度设备并汇总结果。

### 软件功能

- 语音识别 ASR；
- 大模型推理或云端模型适配；
- 语音合成 TTS；
- 会话管理；
- 设备注册和能力模型；
- 自然语言到结构化命令的转换；
- 命令队列和并发策略；
- 超时、取消、重试和幂等；
- 设备状态、事件和历史记录；
- 权限和高风险操作确认；
- MQTT、HTTP、BLE、RS485 等协议适配；
- 本地离线兜底和故障恢复。

### 首版硬件框图

```text
Linux 计算模块
    ├── 本地模型 / 模型 API 适配
    ├── ASR / TTS
    ├── Agent Gateway
    ├── HubService
    ├── SQLite / 本地日志
    ├── MQTT Broker 或 MQTT Client
    └── 设备适配服务

自研中枢底板（后续）
    ├── 稳定 DC 输入和电源保护
    ├── 千兆以太网
    ├── USB Host
    ├── Wi-Fi / BLE
    ├── RS485
    ├── UART / GPIO / I2C / SPI
    ├── eMMC / SSD / NVMe 接口
    ├── 硬件看门狗
    ├── RTC
    ├── 温度检测和风扇接口
    ├── 物理复位 / 恢复按键
    └── 调试串口
```

### 固定式中枢的设计原则

- 先验证模型和实际负载，再确定计算模块；
- 先买现成计算平台，后设计自研底板；
- 计算模块和底板解耦，方便升级算力；
- 中枢可以没有显示屏，显示屏由管理端或随身设备承担；
- 中枢不直接驱动危险执行器，危险动作必须由外设本地闭环负责；
- 中枢断电重启后，命令和设备状态必须可恢复或明确失效。

### 3.3 智能外设

### 产品职责

智能外设负责传感器采集、具体动作、本地安全和状态反馈。

### 两种产品方向

#### A. 自研完整智能硬件

例如：

- 录音豆；
- 智能音箱；
- 灯光设备；
- 温湿度传感器；
- 风扇或低压执行器。

#### B. 传统设备智能化模块

例如：

- 烧水壶控制模块；
- 灯具控制模块；
- 风扇控制模块；
- 红外家电控制模块；
- 机械按键、旋钮或拨杆执行模块。

### 外设必须具备的能力

- 设备身份和能力清单；
- 在线状态和心跳；
- 命令接收和参数校验；
- `command_id` 幂等处理；
- 执行中、成功、失败和取消状态；
- 传感器状态反馈；
- 本地看门狗；
- 断网时的安全默认状态；
- 必要时的实体按键、急停或人工接管。

### 高风险设备原则

烧水壶、微波炉等设备不能采用通用中枢直接控制电源的方式实现。

正确边界是：

```text
中枢：下发目标和任务
设备控制板：采样、判断、调功率和执行安全闭环
执行器：根据本地安全条件动作
设备：返回真实结果和异常
```

烧水壶控制板至少要考虑温度、水位、干烧、过热、本地急停和完成确认。微波炉还要单独考虑门体联锁、微波高压部分和外壳防护。当前阶段不设计 220V 或微波炉高压控制板。

## 4. 三层设备之间的通信协议

### 4.1 随身设备 → 固定式中枢

文字或语音请求统一关联会话和请求编号：

```json
{
  "device_id": "portable_001",
  "conversation_id": "conversation_001",
  "request_id": "request_001",
  "input_type": "audio",
  "payload": "音频数据或音频上传地址",
  "target_device_id": "bean_ye_1",
  "created_at": "2026-10-10T12:00:00Z"
}
```

首版建议：

- 设备配网使用 BLE；
- 语音和文字业务使用 Wi-Fi；
- 语音传输先采用按键说话和短音频上传；
- 后续再增加实时音频流和唤醒词。

### 4.2 固定式中枢 → 随身设备

```json
{
  "request_id": "request_001",
  "response_text": "已经开始录音。",
  "command_id": "command_001",
  "status": "succeeded",
  "audio": "可选的语音回复数据或地址"
}
```

处理中状态必须按 `request_id` 独立返回，不能因为后一条消息到达就覆盖前一条消息。

### 4.3 固定式中枢 ↔ 智能外设

继续复用当前 MQTT 协议和中枢 API，不重新推翻已经验证的链路：

```text
hub/v1/devices/{device_id}/manifest
hub/v1/devices/{device_id}/availability
hub/v1/devices/{device_id}/state
hub/v1/devices/{device_id}/events
hub/v1/devices/{device_id}/commands
hub/v1/devices/{device_id}/command-acks
```

每条动作命令必须关联：

- `command_id`；
- `conversation_id`；
- `request_id`；
- `device_id`；
- `capability`；
- 参数；
- 超时和取消策略。

#### RK3588 联调阶段的协议适配

当前 RK3588 硬件网关使用 HTTP 向子硬件发送统一命令，而真实录音豆仍使用已经验证的 MQTT 协议。阶段 1 不修改录音豆固件，先使用兼容桥转换协议：

```text
RK3588 固定式中枢
  → HTTP POST /command
  → Mac 临时 HTTP-MQTT 兼容桥（19700）
  → HubService / SQLite
  → MQTT
  → bean_ye_1
```

Mac 兼容桥只是阶段 1 的过渡适配层，不承担智能体理解和全局产品职责。后续将 `HubService` 和适配服务迁移到固定式中枢设备后，链路可以收敛为：

```text
随身设备 → RK3588 固定式中枢 → 外设协议适配层 → 智能外设
```

RK3588 注册录音豆时使用桥接主机的局域网地址，不能填写 `127.0.0.1`：

```json
{
  "device_id": "bean_ye_1",
  "name": "录音豆",
  "base_url": "http://192.168.0.107:19700",
  "capabilities": ["record.start", "record.stop", "status.read"]
}
```

## 5. 实施阶段

### 阶段 0：冻结总体规格和接口

**目标：** 不画生产 PCB，先把边界和协议写清楚。

交付物：

- 三层硬件职责表；
- 系统框图；
- 随身设备到中枢的消息格式；
- 中枢到外设的命令格式；
- 命令状态机；
- 离线、超时、取消和高风险操作规则；
- 第一版验收场景。

### 阶段 1：固定式中枢现成平台验证

**目标：** 先证明真实语音、大模型和设备控制可以连起来。

工作内容：

1. 使用 RK3588 作为固定式中枢测试平台；
2. 接入 RK3588 硬件网关的设备注册和命令接口；
3. 通过 HTTP-MQTT 兼容桥接入现有 `bean_ye_1`；
4. 确认 `dispatch=false` 只规划不执行；
5. 确认 `dispatch=true` 能等待真实设备结果；
6. 接入 ASR、模型和 TTS；
7. 保持录音豆原有 MQTT 固件协议不变；
8. 测试多条命令并发、排队、超时和失败恢复。

验收标准：

```text
用户说“开始录音”
  → 中枢识别
  → 智能体生成 record.start
  → 中枢下发给真实录音豆
  → 录音豆执行
  → 中枢收到 succeeded
  → 随身设备播报“已经开始录音”
```

### 阶段 2：随身设备 EVT 原型

**目标：** 替代 Mac 键盘输入，形成真实语音入口。

工作内容：

1. 选联网主控开发板；
2. 接入麦克风和扬声器；
3. 加入按键说话；
4. 加入音频上传和回复播放；
5. 加入电池、充电、保护和电量检测；
6. 加入配网、设备身份和 OTA；
7. 接通阶段 1 的固定式中枢。

首版只做单麦克风、按键说话和短音频，不追求远场拾音、阵列降噪和复杂外观。

### 阶段 3：第一款低风险智能外设

**目标：** 在不接触市电危险部分的前提下验证新的外设类型。

优先顺序：

1. 继续完善真实录音豆；
2. 低压灯光或低压风扇节点；
3. 温湿度等传感器节点；
4. 再评估家电智能化模块。

每款新外设先完成能力模型、状态模型、本地安全和异常反馈，再接入智能体。

### 阶段 4：固定式中枢自研底板

**目标：** 将现成计算平台整合为长期运行的桌面式中枢。

只有在阶段 1 的模型、存储、接口、功耗和温度数据稳定后，才开始：

1. 确定计算模块；
2. 确定电源输入和功耗预算；
3. 分配以太网、USB、RS485、UART、GPIO 等接口；
4. 设计电源树和保护；
5. 设计看门狗、RTC、调试和恢复电路；
6. 画原理图；
7. 设计 PCB；
8. 打样、焊接、启动和压力测试。

### 阶段 5：家电专用智能控制模块

**目标：** 让传统家电具备联网能力，但不牺牲本地安全。

先从低风险、低压、容易验证的设备开始。烧水壶和微波炉必须单独进行安全评审、控制板设计、结构设计和测试，不作为通用外设模块直接复制。

## 8. 第一版整体验收标准

```text
用户按住随身设备按钮说话
  → 随身设备上传真实音频
  → 固定式中枢完成识别
  → 智能体理解命令
  → 中枢生成结构化动作
  → 真实智能外设执行
  → 外设返回真实状态
  → 中枢生成自然语言回复
  → 随身设备播放回复
```

同时验证：

- 前一个命令未完成时可以继续发送后一个命令；
- 每条请求都有独立的 `request_id` 和 `command_id`；
- 设备离线时不伪造成功；
- 外设失败时如实反馈；
- 中枢重启后未完成任务有明确恢复或失效状态；
- 高风险设备必须有本地安全闭环和人工接管方式。
