# RK3588 统一自动路由开发要求

**版本：** V1.0  
**日期：** 2026-10-10  
**适用对象：** RK3588 固定式中枢开发、上位机和随身设备联调

## 1. 开发目标

RK3588 必须提供一个统一的自动路由入口。用户的所有消息都先进入这个入口，由 RK3588 判断消息属于：

```text
chat          普通聊天
clarification  信息不明确，需要用户补充
command       硬件控制命令
```

上位机和随身设备不能自行判断聊天还是硬件命令，也不能因为识别到某个关键词就直接控制硬件。

最终链路必须是：

```text
用户消息
  ↓
RK3588 统一自动路由
  ├─ chat          → 返回聊天回复
  ├─ clarification → 返回澄清问题
  └─ command       → 返回结构化计划
                         ↓
                    用户确认
                         ↓
                    dispatch=true
                         ↓
                    Bridge / HubService / MQTT
                         ↓
                    真实智能硬件
```

## 2. 接口形式

当前推荐接口为 `/api/route`。如果后续更换路径，也必须提供等价能力并同步版本说明。

当前上位机已经按以下形式接入：

```http
POST /api/route
Content-Type: application/json
```

请求至少包含：

```json
{
  "protocol_version": "1.0",
  "request_id": "request-20261010-0001",
  "conversation_id": "conversation-001",
  "source": "desktop",
  "task": "auto",
  "input": "你好",
  "target_device_id": "bean_ye_1"
}
```

字段要求：

| 字段 | 要求 |
| --- | --- |
| `protocol_version` | 当前必须为 `1.0` |
| `request_id` | 每条用户消息唯一；重试必须复用原值 |
| `conversation_id` | 同一轮连续对话复用 |
| `source` | 例如 `desktop`、`portable` |
| `task` | 当前必须为 `auto` |
| `input` | 用户原始文字 |
| `target_device_id` | 可选，当前目标设备；没有目标时允许不传 |

如果接口名称或字段名称不同，必须提供明确的兼容说明，不能让上位机猜测返回格式。

## 3. 路由结果

### 3.1 普通聊天

用户输入“你好”“你能做什么”等内容时，返回：

```json
{
  "protocol_version": "1.0",
  "request_id": "request-20261010-0001",
  "conversation_id": "conversation-001",
  "route": "chat",
  "reply": "你好，我可以帮你查询和控制已接入的智能设备。"
}
```

要求：

- 上位机直接显示 `reply`；
- 不生成 `plan_id`；
- 不调用 Bridge；
- 不发布 MQTT；
- 不要求用户确认硬件动作。

### 3.2 需要澄清

当目标设备、动作或参数不明确时，返回：

```json
{
  "protocol_version": "1.0",
  "request_id": "request-20261010-0002",
  "conversation_id": "conversation-001",
  "route": "clarification",
  "reply": "你是想查询录音状态，还是开始新的录音？"
}
```

要求：

- 上位机显示澄清问题；
- 不生成硬件命令；
- 不调用 Bridge；
- 不发布 MQTT。

### 3.3 硬件命令计划

例如用户输入“请帮我开始录音”：

```json
{
  "protocol_version": "1.0",
  "request_id": "request-20261010-0003",
  "conversation_id": "conversation-001",
  "route": "command",
  "status": "planned",
  "plan_id": "plan-unique-id",
  "reply": "准备让录音豆开始录音。",
  "requires_confirmation": true,
  "command": {
    "device_id": "bean_ye_1",
    "capability": "record.start",
    "params": {}
  }
}
```

要求：

- 必须返回有效的 `plan_id`；
- `command.capability` 必须使用能力白名单，例如 `record.start`；
- `command.params` 必须是 JSON 对象；
- 规划阶段不能调用 Bridge；
- 规划阶段不能发布 MQTT；
- 规划阶段不能改变真实设备状态；
- `record.start`、`record.stop` 默认要求用户确认。

## 4. 快速路由

以下表达必须优先走 `fast_rule`，不能因为简单命令导致模型长时间等待：

| 用户表达 | `capability` |
| --- | --- |
| 开始录音、启动录音、开始记录 | `record.start` |
| 停止录音、结束录音、停止记录 | `record.stop` |
| 查询状态、查看录音状态、读取设备状态 | `status.read` |

响应中建议返回：

```json
{
  "route": "command",
  "route_detail": "fast_rule",
  "status": "planned",
  "plan_id": "plan-unique-id",
  "command": {
    "device_id": "bean_ye_1",
    "capability": "status.read",
    "params": {}
  },
  "requires_confirmation": false
}
```

`status.read` 可以不要求用户确认，但仍然必须经过计划绑定和执行链路，不能由上位机直接访问设备 MQTT。

## 5. 计划确认和执行

用户确认后，上位机发送执行请求：

```http
POST /api/hub/v1/commands
Content-Type: application/json
```

```json
{
  "protocol_version": "1.0",
  "request_id": "execute-20261010-0001",
  "conversation_id": "conversation-001",
  "source": "desktop",
  "plan_id": "plan-unique-id",
  "target_device_id": "bean_ye_1",
  "dispatch": true
}
```

执行前必须校验：

- `plan_id` 存在且未过期；
- 计划中的设备与执行请求一致；
- 计划中的能力仍在设备能力白名单中；
- 当前请求已经得到用户确认；
- 相同执行 `request_id` 重试不能重复发布 MQTT。

执行结果必须如实返回：

```json
{
  "status": "succeeded",
  "plan_id": "plan-unique-id",
  "command_id": "command-unique-id",
  "device_id": "bean_ye_1",
  "capability": "record.start",
  "state": "succeeded",
  "result": {}
}
```

`accepted`、`queued`、`running`、超时、失败和设备离线都不能伪装成成功。

## 6. 超时和错误处理

当前上位机调用 RK3588 的等待时间为 **15 秒**。RK3588 不能让请求一直保持连接而没有响应。

模型不可用、推理失败或服务繁忙时，应在客户端等待窗口内返回明确 JSON，例如：

```json
{
  "protocol_version": "1.0",
  "request_id": "request-20261010-0004",
  "conversation_id": "conversation-001",
  "route": "error",
  "error_code": "AGENT_TIMEOUT",
  "reply": "智能体暂时没有响应，请稍后重试。"
}
```

禁止：

- HTTP 长时间无响应；
- 只返回一段自然语言，让上位机猜测是不是命令；
- 规划失败时让上位机绕过计划直接控制硬件；
- 把聊天消息误报为硬件执行失败；
- 把硬件执行失败误报为聊天成功。

## 7. 日志要求

每条请求至少记录：

```text
protocol_version
request_id
conversation_id
source
route=chat|clarification|command|error
route_detail=fast_rule|llm|asr_llm|clarification
target_device_id
capability
plan_id
dispatch
elapsed_ms
result_status
error_code
```

重点确认：

- `chat` 和 `clarification` 没有调用 Bridge；
- `dispatch=false` 阶段没有调用 Bridge；
- 只有 `dispatch=true` 且计划确认后才进入硬件执行链路；
- 超时请求有明确日志，不是无日志挂起。

## 8. 必须通过的验收用例

### 8.1 普通聊天

输入：

```text
你好
你能做什么
```

预期：

- `route=chat`；
- 返回 `reply`；
- 不产生 `plan_id`；
- 不调用 Bridge；
- 不发布 MQTT。

### 8.2 硬件查询

输入：

```text
帮我看看录音豆现在的状态
```

预期：

- 命中 `fast_rule`；
- 生成 `status.read` 计划；
- 执行后返回真实设备结果；
- 不把设备离线或空状态误报成在线。

### 8.3 开始录音

输入：

```text
请帮我开始录音
```

预期：

- 返回 `route=command`；
- 返回 `record.start` 和有效 `plan_id`；
- 首次请求不发布 MQTT；
- 用户确认后才允许 `dispatch=true`；
- 最终结果必须来自真实设备 ack。

### 8.4 澄清问题

输入一条目标不明确的消息，预期返回 `route=clarification`，不能自行猜测设备或动作。

### 8.5 幂等和安全

- 相同 `request_id`、相同内容重试返回原结果；
- 相同 `request_id`、不同内容返回冲突错误；
- 无效 `plan_id` 不能执行；
- 过期 `plan_id` 不能执行；
- Bridge 或设备离线时不能返回成功。

## 9. 当前项目配合情况

本项目上位机已经按统一自动路由模式改造：

- 所有聊天输入调用 RK3588 `task=auto`；
- `chat` 结果直接显示；
- `clarification` 结果直接显示；
- 硬件计划必须携带 `plan_id`；
- 上位机不会直接发布 MQTT；
- 原有 `dispatch=false`、确认、`dispatch=true` 硬件链路继续保留。

目前实测硬件网关的 `fast_rule`、`plan_id`、Bridge、MQTT 和真实 `status.read` 已经打通。待 RK3588 的统一自动路由返回 `chat`、`clarification`、`command` 三类结构化结果后，即可完成聊天层联调。
