# RK3588 固定式中枢网关开发需求清单

**文档用途：** 提供给 RK3588 固定式中枢开发人员，作为当前阶段的开发、联调和验收依据。  
**版本：** V1.0  
**日期：** 2026-10-10  
**当前目标：** 先完成文字指令到真实录音豆的安全闭环，暂不执行真实录音动作。

## 1. 项目定位

RK3588 是固定式中枢，负责：

- 接收随身设备或上位机发送的文字、后续也可接收音频；
- 对用户输入进行快速意图识别或调用智能体；
- 将自然语言整理为结构化设备动作；
- 校验设备、能力和参数；
- 管理规划、确认、执行和结果返回；
- 通过 HTTP 调用中枢端的设备适配服务。

RK3588 **不直接连接录音豆的 MQTT，不直接操作录音豆固件，也不负责录音豆的 GPIO、麦克风或文件保存逻辑**。

当前真实链路：

```text
用户/随身设备/上位机
        ↓ HTTP JSON
RK3588 固定式中枢
        ↓ HTTP POST /command
中枢端 HTTP-MQTT 兼容桥
        ↓ HubService / MQTT
真实录音豆 bean_ye_1
        ↓ MQTT ack/state
中枢端兼容桥
        ↓ HTTP 结果
RK3588
```

## 2. 当前联调配置

以下地址是当前开发联调地址，不代表量产固定地址，后续应改为配置项：

| 项目 | 当前值 |
| --- | --- |
| RK3588 服务 | `http://192.168.0.140:8095` |
| 中枢端 HTTP-MQTT 桥 | `http://192.168.0.107:19700` |
| 桥健康检查 | `GET /health` |
| 桥命令接口 | `POST /command` |
| 真实设备 ID | `bean_ye_1` |
| 设备显示名 | `录音豆` |
| 设备能力 | `record.start`、`record.stop`、`status.read` |

注意：RK3588 注册设备时，`base_url` 必须填写 RK3588 能访问到的中枢端局域网地址：

```json
{
  "device_id": "bean_ye_1",
  "name": "录音豆",
  "base_url": "http://192.168.0.107:19700",
  "capabilities": ["record.start", "record.stop", "status.read"]
}
```

不能填写：

- 录音豆自身的 IP；
- RK3588 上的 `127.0.0.1`；
- 中枢端电脑上的 `127.0.0.1`。

## 3. 必须提供的 HTTP API

### 3.1 网关健康检查

```http
GET /api/health
```

至少返回：

```json
{
  "status": "ok",
  "model": "当前实际加载的模型名称"
}
```

如果模型或语音服务未就绪，应返回明确状态，不要一直保持 HTTP 连接无响应。

### 3.2 硬件网关健康检查

```http
GET /api/hub/v1/health
```

建议返回：

```json
{
  "status": "ok",
  "service": "rk3588-hardware-gateway",
  "devices": [
    {
      "device_id": "bean_ye_1",
      "name": "录音豆",
      "capabilities": ["record.start", "record.stop", "status.read"]
    }
  ],
  "api_key_required": false
}
```

`devices` 表示 RK3588 当前保存的设备注册信息，不应在没有探测或心跳依据时直接声称设备物理在线。若网关能探测 `base_url`，建议额外返回：

```json
{
  "online": true,
  "last_seen": "2026-10-10T12:00:00Z",
  "reachable": true
}
```

### 3.3 查询设备目录

```http
GET /api/hub/v1/devices
```

服务重启后设备目录可以清空，因此中枢端会在启动后重新注册。重复注册同一个 `device_id` 必须更新配置，而不是创建重复设备。

### 3.4 注册或更新设备

```http
POST /api/hub/v1/devices
Content-Type: application/json
```

请求：

```json
{
  "device_id": "bean_ye_1",
  "name": "录音豆",
  "base_url": "http://192.168.0.107:19700",
  "capabilities": ["record.start", "record.stop", "status.read"]
}
```

成功返回：

```json
{
  "ok": true,
  "device": {
    "device_id": "bean_ye_1",
    "name": "录音豆",
    "capabilities": ["record.start", "record.stop", "status.read"]
  }
}
```

注册接口应支持幂等调用。中枢端会在以下时机调用：

1. 中枢端程序启动后；
2. RK3588 网关恢复后；
3. 定期检查发现 `bean_ye_1` 不在设备列表时；
4. 注册失败后按指数退避重试。

### 3.5 硬件命令入口

```http
POST /api/hub/v1/commands
Content-Type: application/json
```

文字规划请求：

```json
{
  "request_id": "plan-20261010-0001",
  "input": "开始录音",
  "target_device": "bean_ye_1",
  "dispatch": false
}
```

语音规划请求可以使用：

```json
{
  "request_id": "plan-20261010-0002",
  "audio": "data:audio/wav;base64,...",
  "target_device": "bean_ye_1",
  "dispatch": false
}
```

第一阶段优先保证文字请求稳定，音频请求可以在文字链路通过后接入。

### 3.6 高风险确认接口

```http
POST /api/hub/v1/commands/{request_id}/confirm
```

即使当前 `record.start` 和 `record.stop` 被视为低风险动作，也必须保留该接口，供以后门锁、电机、高压和其他危险设备使用。

## 4. 快速固定指令路由

以下三个意图必须提供本地快速映射，不应为了简单录音控制请求调用 DeepSeek 8B 或其他大模型：

| 用户表达示例 | 结构化动作 |
| --- | --- |
| 开始录音、启动录音、开始记录 | `record.start` |
| 停止录音、结束录音、停止记录 | `record.stop` |
| 查询录音状态、查看状态、读取状态 | `status.read` |

要求：

- 快速路由必须在 RK3588 上实际生效；
- 不能因为模型服务繁忙而让固定指令长时间无响应；
- 未识别的复杂请求才进入通用智能体；
- 请提供连续多次测试结果和响应时间统计，不要只提供一次成功截图；
- 如果快速路由未命中，应在响应或日志中明确记录实际走了哪条路径。

建议日志字段：

```text
request_id
input_type
route=fast_rule|llm|asr_llm|clarification
device_id
action
dispatch
elapsed_ms
result_status
```

## 5. 规划、确认和执行流程

### 5.1 核心安全要求

第一次用户输入不能直接触发真实硬件执行。默认必须按以下流程：

```text
用户输入“开始录音”
        ↓
dispatch=false
        ↓
RK3588 返回结构化计划
        ↓
中枢端展示“将开始录音，是否确认？”
        ↓
用户确认
        ↓
dispatch=true 或 confirm 接口
        ↓
RK3588 调用中枢端 /command
        ↓
HubService 转 MQTT
        ↓
录音豆返回真实 ack
```

### 5.2 规划响应格式

对于“开始录音”，规划响应至少应包含：

```json
{
  "status": "planned",
  "request_id": "plan-20261010-0001",
  "plan_id": "plan-result-unique-id",
  "reply": "准备让录音豆开始录音。",
  "command": {
    "device_id": "bean_ye_1",
    "action": "record.start",
    "params": {}
  },
  "requires_confirmation": true
}
```

`command.action` 必须是设备能力白名单中的值，不能只返回自然语言描述。

### 5.3 执行计划的绑定要求

规划和执行可以使用不同的网络 `request_id`，但执行必须绑定用户刚刚确认的计划，不能只重新发送同一句自然语言让模型再次理解。

推荐执行请求增加 `plan_id`：

```json
{
  "request_id": "execute-20261010-0001",
  "plan_id": "plan-result-unique-id",
  "input": "开始录音",
  "target_device": "bean_ye_1",
  "dispatch": true
}
```

RK3588 应验证：

- `plan_id` 存在且未过期；
- 计划中的设备仍然是 `bean_ye_1`；
- 计划中的动作仍然是 `record.start`；
- 当前设备仍然支持该能力；
- 未确认或已过期的计划不能执行。

如果当前实现暂时不支持 `plan_id`，至少要在接口文档中明确：执行请求如何绑定到已规划的结构化动作，以及网络重试如何保证不重复执行。

### 5.4 执行响应格式

成功时：

```json
{
  "status": "dispatched",
  "request_id": "execute-20261010-0001",
  "plan_id": "plan-result-unique-id",
  "dispatch": {
    "ok": true,
    "device_id": "bean_ye_1",
    "action": "record.start",
    "result": {
      "ok": true,
      "message": "已经开始录音"
    }
  }
}
```

失败、排队或超时不能返回成功：

| 状态 | 含义 | 中枢端处理 |
| --- | --- | --- |
| `planned` | 已规划，未执行 | 等待用户确认 |
| `dispatched` | 已执行并得到真实结果 | 显示设备返回内容 |
| `needs_clarification` | 目标或能力不明确 | 让用户补充信息 |
| `dispatch_failed` | 桥或设备执行失败 | 显示失败原因 |
| `awaiting_confirmation` | 等待确认 | 显示确认操作 |
| `pending` / `queued` | 已接收但未完成 | 不能显示“已完成” |

## 6. 中枢端 HTTP-MQTT 桥协议

RK3588 执行计划时，调用：

```http
POST http://192.168.0.107:19700/command
Content-Type: application/json
```

请求：

```json
{
  "request_id": "execute-20261010-0001",
  "source": "rk3588",
  "command": {
    "device_id": "bean_ye_1",
    "action": "record.start",
    "params": {}
  }
}
```

桥接层行为：

1. 将 `action` 映射为现有 HubService 能力名；
2. 将 HTTP `request_id` 作为 MQTT `command_id`；
3. 调用现有 MQTT 设备协议；
4. 等待录音豆真实 ack；
5. 只有 ack 为 `succeeded` 才返回 `ok: true`；
6. 相同 `request_id` 重试时返回已有命令结果，不再次发布 MQTT；
7. 设备离线、排队、超时、失败都必须明确返回。

桥接成功响应：

```json
{
  "ok": true,
  "request_id": "execute-20261010-0001",
  "command_id": "execute-20261010-0001",
  "device_id": "bean_ye_1",
  "action": "record.start",
  "state": "succeeded",
  "message": "已经开始录音",
  "result": {}
}
```

桥接还支持：

```http
GET http://192.168.0.107:19700/health
```

## 7. 设备目录和重启恢复

RK3588 设备目录当前属于运行时注册信息，服务重启后可能清空。必须支持：

- 中枢端启动后自动注册 `bean_ye_1`；
- RK3588 重启后自动重新注册；
- 定期发现设备缺失后重新注册；
- 注册失败指数退避；
- 界面能够显示“RK3588 未连接”或“设备注册失败”；
- 不把注册成功误认为录音豆当前在线。

建议设备注册信息至少包含：

```json
{
  "device_id": "bean_ye_1",
  "name": "录音豆",
  "base_url": "http://192.168.0.107:19700",
  "capabilities": ["record.start", "record.stop", "status.read"]
}
```

## 8. 错误和安全要求

至少区分以下情况：

| 情况 | 建议状态 |
| --- | --- |
| 参数缺失或格式错误 | HTTP `400` 或 `422` |
| API Key 错误 | HTTP `401` |
| 设备不存在 | HTTP `404` |
| 能力不支持 | HTTP `400` 或 `422` |
| 设备离线或桥不可达 | HTTP `503` |
| 设备执行失败 | `dispatch_failed` |
| 设备等待超时 | `timeout` / `pending` |

生产或跨网络使用时：

- 支持 `HUB_API_KEY` 和 `X-Hub-Key`；
- 不把 `8095` 暴露到公网；
- 日志不记录完整音频、密钥和敏感内容；
- 所有参数由 RK3588 校验一次，设备端仍要再次校验；
- 门锁、电机、高压和危险动作保留人工确认；
- 不允许模型自然语言回复直接绕过结构化命令校验。

## 9. 录音豆端边界

本阶段录音豆继续使用现有 MQTT 固件协议，不需要：

- 监听 `19700`；
- 实现 HTTP `POST /command`；
- 保存 RK3588 地址；
- 运行 ASR 或大模型；
- 理解中文自然语言。

录音豆只需要保证：

- 设备 ID 为 `bean_ye_1`；
- 正确处理 `record.start`、`record.stop`、`status.read`；
- 真实动作完成后再返回 `succeeded`；
- 同一个 `command_id` 重复到达时不重复执行；
- MQTT 重连后恢复在线、心跳、状态和 ack 机制。

## 10. 必须完成的验收用例

### A. 服务和注册

1. `GET /api/health` 返回服务和模型状态；
2. `GET /api/hub/v1/health` 返回网关状态；
3. 注册 `bean_ye_1` 成功；
4. 重复注册不会产生重复设备；
5. RK3588 重启后，中枢端能够重新注册设备。

### B. 快速规划

1. 发送“开始录音”，返回 `planned` 和 `record.start`；
2. 发送“停止录音”，返回 `planned` 和 `record.stop`；
3. 发送“查询录音状态”，返回 `planned` 和 `status.read`；
4. 规划阶段不能调用桥的 `/command`；
5. 规划阶段不能发布 MQTT 命令；
6. 连续测试至少 10 次，记录每次耗时和路由类型；
7. 模型服务暂时不可用时，固定指令仍能走快速路由。

### C. 确认和执行

1. 未确认的计划不能执行；
2. 已确认的计划只能执行计划中的设备和动作；
3. 桥返回成功必须对应录音豆真实 `succeeded` ack；
4. 桥返回 `pending`、失败或超时不能显示“录音已开始”；
5. 同一个执行 `request_id` 重试不能重复发送 MQTT；
6. 新的用户操作必须使用新的 `request_id`；
7. 开始录音和停止录音连续发送时，两个请求都能独立追踪。

### D. 异常场景

1. 录音豆离线；
2. MQTT Broker 断开；
3. 桥服务不可达；
4. 设备返回失败 ack；
5. 设备长时间不返回 ack；
6. `request_id` 重复但参数不同；
7. RK3588 重启后设备目录为空；
8. 目标设备或能力不存在。

## 11. 本阶段明确不要求

- 不要求修改录音豆现有 MQTT 主题和命令格式；
- 不要求 RK3588 直接连接 MQTT Broker；
- 不要求立即接入随身设备实物；
- 不要求立即完成音频流和实时语音；
- 不要求接入烧水壶、微波炉、门锁或 220V 设备；
- 不要求在 RK3588 上重新设计硬件电路；
- 不要求第一次就接入复杂多智能体编排；
- 不允许为了测试直接执行真实录音命令。

## 12. 请 RK3588 开发完成后提供

1. RK3588 服务版本号和部署时间；
2. 实际启用的 API 路径和请求示例；
3. 快速路由规则及 10 次以上测试结果；
4. `dispatch=false` 的完整响应示例；
5. `plan_id` 或其他计划确认绑定方式；
6. `dispatch=true` 的完整响应示例，但先不要对真实录音豆执行；
7. 设备注册、重启恢复和失败重试说明；
8. 错误码和日志字段说明；
9. 运行日志中确认规划阶段没有访问 `/command` 或发布 MQTT；
10. 所有变更的代码版本、配置文件和启动命令。

## 13. 完成后的继续步骤

RK3588 开发完成并通过本清单的 A、B 项后，再由中枢端继续：

1. 联调验证中枢端已实现的自动设备注册和健康检查；
2. 接入规划结果展示；
3. 接入用户确认按钮；
4. 先用桥接层做一次无硬件执行链路验证；
5. 获得明确授权后，执行第一次真实 `record.start`；
6. 验证 `record.stop`、状态查询、排队、超时和重复请求。

在 RK3588 的 `dispatch=false` 稳定返回结构化计划之前，不执行真实录音命令。
