# 随身设备与固定式中枢接口协议

**协议名称：** Portable-Hub Interface  
**版本：** V1.0 草案  
**日期：** 2026-10-10  
**状态：** 阶段 0 设计稿；文字请求和音频上传入口已实现，完成首轮评审后冻结

## 1. 目标

本协议定义随身设备与固定式中枢之间的边界，不涉及中枢与智能外设之间已经存在的 MQTT 设备协议。

随身设备负责：

- 采集用户语音或文字；
- 上传用户输入；
- 接收处理中状态；
- 播放或显示中枢回复；
- 展示网络、设备和错误状态。

固定式中枢负责：

- 接收请求并维护会话；
- 语音识别；
- 调用智能体或大模型；
- 生成结构化动作；
- 调用现有 `HubService` 下发设备命令；
- 汇总真实设备结果；
- 返回文字和可选语音回复。

随身设备不直接连接智能外设，也不直接操作 MQTT。

### 核心决策：随身设备不负责语音转文字

第一版随身设备只采集、编码和上传原始音频。语音理解统一放在固定式中枢，原因是：

- 随身设备可以使用更低功耗的主控；
- ASR、音频模型和大模型可以独立升级；
- 语音识别失败时可以切换其他理解方式；
- 后续更换随身设备时，不需要重新迁移智能体逻辑；
- 中枢可以统一保存请求、音频和执行结果之间的关联。

“智能体直接读取音频”可以作为固定式中枢的可选能力，但不能让模型直接绕过中枢命令校验去控制硬件。

## 2. 首版传输方式

### 2.1 业务连接

首版使用固定式中枢局域网地址提供 HTTP API：

```text
随身设备 ── Wi-Fi / HTTP ──> 固定式中枢
```

选择 HTTP 的原因：

- 随身设备容易实现；
- 便于抓包、调试和复现；
- 与当前 Python 中枢服务兼容；
- 不要求第一版引入 WebSocket 服务端；
- 后续可以在不改变消息结构的情况下增加 WebSocket 或实时音频通道。

### 2.2 首版输入顺序

首版按以下顺序实现：

1. 文字请求；
2. 短音频上传；
3. 中枢音频理解；
4. 实时音频流；
5. 唤醒词和连续对话。

第一版随身设备采用“按键说话”，不先做复杂的本地唤醒词，避免把语音唤醒、降噪、回声消除和智能体链路同时引入。

### 2.3 中枢音频理解模式

固定式中枢预留三种模式，实际部署时按模型能力和成本选择：

```text
模式 A：原始音频 → ASR → 文字 → 智能体
模式 B：原始音频 → 支持音频输入的智能体 → 结构化意图
模式 C：原始音频 → ASR + 音频智能体 → 交叉确认 → 结构化意图
```

模式 A 最容易调试和审计；模式 B 可以减少单独 ASR 的一跳；模式 C 适合需要同时保留文字记录、说话人信息或音频语气信息的场景。

无论使用哪种模式，最终都必须输出统一的结构化意图，再交给 `HubService` 做设备能力、权限、队列和安全校验。

## 3. 标识和基本约束

### 3.1 标识

| 字段 | 说明 | 生成方 |
| --- | --- | --- |
| `portable_device_id` | 随身设备唯一 ID | 设备出厂或首次配网 |
| `conversation_id` | 一段连续对话的 ID | 随身设备或中枢 |
| `request_id` | 一次用户输入的 ID | 随身设备 |
| `command_id` | 一条实际硬件命令的 ID | 固定式中枢 |
| `media_id` | 一段已上传音频的 ID | 固定式中枢 |

### 3.2 约束

- 所有 ID 使用非空字符串；
- `request_id` 在同一随身设备上必须唯一；
- 同一个 `request_id` 重试时，中枢必须幂等处理，不得重复执行硬件命令；
- 每条请求独立返回状态，不能因为新请求到达而覆盖旧请求；
- `conversation_id` 用于维持上下文，不用于替代 `request_id`；
- `command_id` 只在中枢决定执行硬件动作后产生；
- 查询类请求可以没有 `command_id`。

## 4. 请求接口

### 4.1 创建文字或音频请求

```text
POST /api/v1/portable/v1/requests
Content-Type: application/json
```

请求示例：

```json
{
  "portable_device_id": "portable_001",
  "conversation_id": "conversation_001",
  "request_id": "request_001",
  "input_type": "text",
  "text": "开始录音",
  "target_device_id": "bean_ye_1",
  "client_created_at": "2026-10-10T12:00:00+08:00",
  "client_timezone": "Asia/Shanghai"
}
```

音频请求示例：

```json
{
  "portable_device_id": "portable_001",
  "conversation_id": "conversation_001",
  "request_id": "request_002",
  "input_type": "audio",
  "media_id": "media_001",
  "target_device_id": "bean_ye_1",
  "client_created_at": "2026-10-10T12:00:05+08:00",
  "client_timezone": "Asia/Shanghai"
}
```

### 4.2 创建请求的响应

中枢收到请求后立即返回，不等待硬件执行完成：

```http
HTTP/1.1 202 Accepted
Content-Type: application/json
```

```json
{
  "request_id": "request_001",
  "conversation_id": "conversation_001",
  "state": "received",
  "status_url": "/api/v1/portable/v1/requests/request_001",
  "events_url": "/api/v1/portable/v1/requests/request_001/events"
}
```

### 4.3 查询请求状态

```text
GET /api/v1/portable/v1/requests/{request_id}
```

处理中示例：

```json
{
  "request_id": "request_001",
  "conversation_id": "conversation_001",
  "portable_device_id": "portable_001",
  "state": "executing",
  "input_type": "text",
  "text": "开始录音",
  "intent": {
    "capability": "record.start",
    "device_id": "bean_ye_1",
    "params": {}
  },
  "command_id": "command_001",
  "response_text": "正在开始录音…",
  "created_at": "2026-10-10T12:00:00+08:00",
  "updated_at": "2026-10-10T12:00:01+08:00"
}
```

完成示例：

```json
{
  "request_id": "request_001",
  "conversation_id": "conversation_001",
  "portable_device_id": "portable_001",
  "state": "succeeded",
  "input_type": "text",
  "text": "开始录音",
  "intent": {
    "capability": "record.start",
    "device_id": "bean_ye_1",
    "params": {}
  },
  "command_id": "command_001",
  "response_text": "已经开始录音。",
  "result": {
    "recording": true
  },
  "created_at": "2026-10-10T12:00:00+08:00",
  "updated_at": "2026-10-10T12:00:02+08:00"
}
```

## 5. 请求状态机

### 5.1 请求状态

```text
received
    ↓
transcribing       仅音频请求使用
    ↓
understanding
    ↓
planned
    ├── completed    纯对话或查询已经完成
    └── queued       已生成硬件命令，等待设备执行
                       ↓
                    executing
                       ├── succeeded
                       ├── failed
                       ├── cancelled
                       ├── superseded
                       └── timed_out
```

### 5.2 状态含义

| 状态 | 含义 |
| --- | --- |
| `received` | 中枢已收到请求并完成基础校验 |
| `transcribing` | 中枢正在把音频转换为文字 |
| `understanding` | 智能体正在理解用户意图 |
| `planned` | 已经得到回复或结构化动作计划 |
| `queued` | 硬件命令已经进入设备队列 |
| `executing` | 对应硬件命令正在执行 |
| `completed` | 不需要硬件动作的请求已经完成 |
| `succeeded` | 硬件动作已真实成功 |
| `failed` | 硬件或中枢执行失败 |
| `cancelled` | 请求或对应命令已取消 |
| `superseded` | 被更新的命令替代 |
| `timed_out` | 在约定时间内没有得到最终结果 |

`queued`、`executing` 和 `timed_out` 都不能向用户表达为“动作已经完成”。

## 6. 事件接口

### 6.1 单请求事件流

```text
GET /api/v1/portable/v1/requests/{request_id}/events
Accept: text/event-stream
```

首版使用 SSE 推送状态，事件格式沿用当前中枢事件流的风格：

```text
event: request.updated
data: {"request_id":"request_001","state":"executing","command_id":"command_001"}

event: request.updated
data: {"request_id":"request_001","state":"succeeded","response_text":"已经开始录音。"}
```

随身设备收到终态后可以关闭事件连接，也可以继续使用状态查询接口确认结果。

### 6.2 多请求并发

随身设备可以在 `request_001` 仍处于 `executing` 时发送 `request_002`：

```text
request_001 → conversation_001 → command_001 → executing
request_002 → conversation_001 → command_002 → queued
```

两个请求必须分别维护状态和回复。中枢不能因为它们属于同一个 `conversation_id`，就把两个请求合并成一条不可追踪的任务。

## 7. 音频上传接口

首版不把大段 Base64 音频直接塞进请求 JSON。采用先上传、后引用的方式：

```text
POST /api/v1/portable/v1/media
Content-Type: application/octet-stream
X-Portable-Device-Id: portable_001
X-Media-Type: audio
X-Audio-Format: wav
```

响应：

```json
{
  "media_id": "media_001",
  "media_type": "audio",
  "state": "stored",
  "expires_at": "2026-10-10T12:10:00+08:00"
}
```

然后在请求接口中使用 `media_id`。

首版音频格式、采样率和编码方式不在协议中写死，由随身设备能力清单和中枢音频理解配置协商。第一版先支持一种稳定格式，确定实际麦克风、模型输入要求和网络传输方式后再冻结具体参数。

## 8. 错误格式

所有业务错误统一返回：

```json
{
  "error": {
    "code": "DEVICE_OFFLINE",
    "message": "目标设备当前离线，命令没有执行。",
    "request_id": "request_001",
    "command_id": "command_001",
    "retryable": true
  }
}
```

首版错误码：

| 错误码 | 含义 |
| --- | --- |
| `INVALID_REQUEST` | 请求字段缺失或格式错误 |
| `DUPLICATE_REQUEST` | 请求 ID 与已有请求冲突 |
| `UNKNOWN_CONVERSATION` | 会话不存在或已过期 |
| `AUDIO_NOT_FOUND` | 音频媒体不存在或已过期 |
| `TRANSCRIPTION_FAILED` | 语音识别失败 |
| `INTENT_NOT_SUPPORTED` | 当前智能体不支持该意图 |
| `DEVICE_NOT_FOUND` | 目标设备不存在 |
| `DEVICE_OFFLINE` | 目标设备离线 |
| `CAPABILITY_NOT_SUPPORTED` | 设备不具备目标能力 |
| `COMMAND_TIMEOUT` | 硬件命令超时 |
| `COMMAND_FAILED` | 硬件命令执行失败 |
| `HUB_UNAVAILABLE` | 固定式中枢暂时不可用 |

## 9. 安全和配对

### 阶段 0 / 局域网联调

- 随身设备首次通过配对码加入中枢；
- 中枢为设备分配或确认 `portable_device_id`；
- 允许使用局域网明文 HTTP 进行开发联调；
- 不把开发网络配置直接用于量产产品；
- 日志中不记录完整音频内容和敏感用户信息。

### 产品化前必须补齐

- HTTPS 或局域网加密通道；
- 随身设备身份凭证；
- 设备撤销和重新配对；
- 固件签名和 OTA 校验；
- 高风险命令的二次确认；
- 音频、会话和设备日志的存储周期。

## 10. 与现有中枢软件的映射

| 新协议对象 | 现有实现或后续实现 |
| --- | --- |
| 随身设备请求 | 新增 Portable Request 层 |
| `conversation_id` | 继续传给 `TextAgent` 或未来大模型 Agent |
| `request_id` | 新增请求级状态和幂等记录 |
| `command_id` | 复用现有 `HubService` 命令生命周期 |
| `capability` | 复用现有设备能力模型 |
| `queued` / `executing` | 复用现有命令状态和事件流 |
| 设备结果 | 复用现有 MQTT ack 和 state |
| 文字回复 | 返回给随身设备或桌面上位机 |
| 原始音频 | 由音频理解适配器处理，可走 ASR、直接音频智能体或混合模式 |
| 语音回复 | 后续由 TTS 生成并通过媒体接口返回 |

本协议不修改现有 MQTT 主题、不修改 ESP32 设备命令格式，也不要求录音豆立即升级固件。

## 11. 阶段 0 完成标准

阶段 0 完成后，应当能够回答以下问题：

1. 随身设备如何发送一条文字请求；
2. 随身设备如何发送一段音频请求；
3. 中枢如何返回处理中和最终状态；
4. 两条并发请求如何分别追踪；
5. 请求重试如何避免重复执行；
6. 中枢如何把请求关联到现有 `command_id`；
7. 设备离线时如何反馈；
8. 以后增加 WebSocket、实时语音或 TTS 时哪些字段可以复用。

阶段 0 的下一项实现任务是：

```text
接入音频理解适配器，首选先实现 `ASR → 文字智能体`，同时保留直接音频智能体的接口。
```

当前已完成的代码入口：

```text
POST /api/v1/portable/v1/media
POST /api/v1/portable/v1/requests
GET  /api/v1/portable/v1/requests/{request_id}
```

当前音频请求如果没有配置音频理解适配器，会返回 `AUDIO_UNDERSTANDING_NOT_CONFIGURED`，不会生成或下发硬件命令。
