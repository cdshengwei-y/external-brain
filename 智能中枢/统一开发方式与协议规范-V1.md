# 外接大脑统一开发方式与协议规范

**协议版本：** V1.0  
**发布日期：** 2026-10-10  
**适用范围：** 随身设备、固定式中枢 RK3588、中枢端 HubService、HTTP-MQTT 兼容桥、智能外设  
**当前首个真实设备：** `bean_ye_1` 录音豆

> 从本文件发布起，新增代码、接口、测试和联调以本文件为唯一 V1 依据。旧文档中的字段名、示例和流程如果与本文件冲突，以本文件为准；兼容旧字段时必须明确标注为兼容别名。

## 1. 统一架构

系统固定分为四层：

```text
随身设备 / 桌面上位机
        ↓ HTTP JSON
固定式中枢 RK3588
        ↓ HTTP JSON
中枢端协议适配层
        ↓ MQTT / HTTP / 其他设备协议
智能外设
```

当前录音豆的过渡链路：

```text
随身设备或上位机
  → RK3588 智能体网关
  → 中枢端 HTTP-MQTT Bridge
  → HubService / SQLite
  → MQTT
  → bean_ye_1
```

### 1.1 各层职责

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 随身设备/上位机 | 采集文字或音频、显示处理中和结果、请求确认 | 不直接操作 MQTT，不直接控制外设 |
| RK3588 | ASR、快速意图路由、智能体理解、计划生成、风险控制 | 不直接连接录音豆 MQTT，不直接操作 GPIO |
| HubService/适配桥 | 设备能力校验、命令队列、幂等、超时、协议转换、结果等待 | 不理解自然语言 |
| 智能外设 | 执行动作、状态采集、本地安全闭环、返回 ack | 不理解中文，不运行大模型 |

### 1.2 重要边界

- RK3588 不直接连接录音豆 MQTT。
- 录音豆不直接访问 RK3588。
- 中枢端不能把自然语言回复直接当作硬件命令执行。
- 所有硬件动作必须先变成结构化能力，再经过设备能力校验。
- 未经用户确认的计划不能调用真实执行链路。
- 本 V1 不涉及烧水壶、微波炉、门锁、220V 或微波高压控制。

## 2. 统一命名

### 2.1 字段名称冻结

| 含义 | V1 标准字段 | 说明 |
| --- | --- | --- |
| 用户请求 | `request_id` | 一次网络请求/用户操作的唯一 ID |
| 会话 | `conversation_id` | 连续对话上下文，不用于幂等 |
| 计划 | `plan_id` | RK3588 生成的一条不可随意修改的结构化计划 |
| 硬件命令 | `command_id` | HubService 创建的一条实际设备命令 |
| 设备 ID | `device_id` | 设备唯一身份，例如 `bean_ye_1` |
| 设备能力 | `capability` | 标准使用点号格式，例如 `record.start` |
| 动作参数 | `params` | JSON 对象，不能使用自由文本代替 |
| 目标设备 | `target_device_id` | 请求阶段指定的设备 ID |
| 命令来源 | `source` | 例如 `rk3588`、`portable`、`desktop` |
| 协议版本 | `protocol_version` | 当前固定为 `1.0` |

### 2.2 兼容别名

为了兼容已经部署的 RK3588 代码：

- `action` 可以作为 `capability` 的旧别名接收；
- `target_device` 可以作为 `target_device_id` 的旧别名接收；
- 新代码和新文档必须使用 `capability`、`target_device_id`；
- 同一个请求不能同时提供标准字段和兼容别名；
- 兼容别名只能在接口边界转换一次，进入 HubService 后统一使用标准字段。

示例：

```json
{
  "device_id": "bean_ye_1",
  "capability": "record.start",
  "params": {}
}
```

旧格式可以被桥接层接受，但不得继续扩散：

```json
{
  "device_id": "bean_ye_1",
  "action": "record.start",
  "params": {}
}
```

## 3. ID 和幂等规则

### 3.1 `conversation_id`

- 表示一段连续对话；
- 同一轮上位机运行期间可以复用；
- 可以关联多条 `request_id`；
- 不能用来判断请求是否重复；
- 不能替代 `request_id` 或 `command_id`。

### 3.2 `request_id`

- 每个新的用户操作生成一个新的 `request_id`；
- 同一次网络重试必须复用原 `request_id`；
- 相同 `request_id` 且参数相同，必须返回已有结果；
- 相同 `request_id` 但设备、能力或参数不同，必须返回冲突错误；
- 不得因为新请求到达而覆盖旧请求状态。

### 3.3 `plan_id`

- 每次规划成功生成一个唯一 `plan_id`；
- `plan_id` 绑定设备、能力、参数、创建时间和过期时间；
- 用户确认时必须提交 `plan_id`；
- 计划过期、设备变化或能力变化后不得直接执行；
- 不允许仅凭再次发送相同中文句子来代替计划确认。

### 3.4 `command_id`

- 只有真正准备进入硬件执行链路时才创建；
- 一个 `command_id` 只对应一次实际硬件命令；
- MQTT ack 必须携带同一个 `command_id`；
- 当前兼容桥可以暂时令 `command_id` 等于执行请求的 `request_id`，但调用方必须以返回的 `command_id` 为准，不能依赖两者永久相同；
- 重试不能创建第二个硬件命令。

## 4. 标准能力模型

### 4.1 能力命名

统一使用：

```text
对象.动作
```

当前录音豆能力：

```text
record.start
record.stop
status.read
```

后续示例：

```text
light.turn_on
light.turn_off
fan.speed.set
kettle.start
```

能力名必须是白名单值，不能把自然语言直接放在 `capability` 中。

### 4.2 当前快速路由

以下表达必须优先走 RK3588 本地快速映射，不依赖大模型：

| 表达 | 标准能力 |
| --- | --- |
| 开始录音、启动录音、开始记录 | `record.start` |
| 停止录音、结束录音、停止记录 | `record.stop` |
| 查询录音状态、查看状态、读取状态 | `status.read` |

快速路由要求：

- 不产生硬件副作用；
- `dispatch=false` 时只生成计划；
- 规则未命中才进入通用智能体；
- 模型服务不可用时，固定指令仍应可规划；
- 日志必须记录实际路由为 `fast_rule`、`llm` 或 `clarification`。

## 5. RK3588 网关接口

### 5.1 健康检查

```http
GET /api/health
```

```json
{
  "status": "ok",
  "model": "当前加载模型名称"
}
```

接口必须在服务未就绪时明确返回错误或非就绪状态，不能长时间无响应。

### 5.2 硬件网关健康检查

```http
GET /api/hub/v1/health
```

```json
{
  "status": "ok",
  "service": "rk3588-hardware-gateway",
  "devices": [],
  "api_key_required": false
}
```

`devices` 是注册目录，不自动等同于设备物理在线。若能够探测设备，在线字段必须单独表达。

### 5.3 设备注册

```http
POST /api/hub/v1/devices
Content-Type: application/json
```

```json
{
  "device_id": "bean_ye_1",
  "name": "录音豆",
  "base_url": "http://192.168.0.107:19700",
  "capabilities": ["record.start", "record.stop", "status.read"]
}
```

要求：

- 相同 `device_id` 重复注册必须幂等更新；
- `base_url` 必须是 RK3588 可以访问的真实局域网地址；
- 不能填写其他设备的 `127.0.0.1`；
- 设备服务重启后允许重新注册；
- 设备目录为空时不能把设备当作已在线。

### 5.4 规划请求

```http
POST /api/hub/v1/commands
Content-Type: application/json
```

标准文字请求：

```json
{
  "protocol_version": "1.0",
  "request_id": "plan-20261010-0001",
  "conversation_id": "conversation-001",
  "input": "开始录音",
  "target_device_id": "bean_ye_1",
  "dispatch": false
}
```

兼容旧实现时，可以暂时接收 `target_device`，但返回和新代码统一使用 `target_device_id`。

成功规划必须返回结构化计划：

```json
{
  "status": "planned",
  "protocol_version": "1.0",
  "request_id": "plan-20261010-0001",
  "plan_id": "plan-result-unique-id",
  "reply": "准备让录音豆开始录音。",
  "requires_confirmation": true,
  "command": {
    "device_id": "bean_ye_1",
    "capability": "record.start",
    "params": {}
  }
}
```

规划阶段禁止：

- 调用中枢端 `/command`；
- 发布 MQTT 命令；
- 改变录音豆状态；
- 只返回自然语言而不返回结构化能力。

### 5.5 执行请求

用户确认后提交：

```json
{
  "protocol_version": "1.0",
  "request_id": "execute-20261010-0001",
  "conversation_id": "conversation-001",
  "plan_id": "plan-result-unique-id",
  "target_device_id": "bean_ye_1",
  "dispatch": true
}
```

执行前必须验证：

- `plan_id` 存在且没有过期；
- 计划中的 `device_id` 与目标设备一致；
- 计划中的 `capability` 仍在设备能力白名单中；
- 设备注册信息和 `base_url` 有效；
- 当前操作确实已得到用户确认。

如果当前版本暂时无法提供 `plan_id`，必须明确说明执行请求如何绑定已规划动作，不能默默重新调用模型理解。

### 5.6 确认接口

```http
POST /api/hub/v1/commands/{request_id}/confirm
```

高风险动作必须走确认接口。即使当前录音动作被认为是低风险，也必须保留接口和状态，以便后续扩展门锁、电机等设备。

## 6. 中枢端 HTTP-MQTT Bridge 协议

RK3588 执行结构化计划时调用：

```http
POST http://192.168.0.107:19700/command
Content-Type: application/json
```

标准请求：

```json
{
  "protocol_version": "1.0",
  "request_id": "execute-20261010-0001",
  "source": "rk3588",
  "command": {
    "device_id": "bean_ye_1",
    "capability": "record.start",
    "params": {}
  }
}
```

兼容阶段可以接受：

```json
{
  "command": {
    "device_id": "bean_ye_1",
    "action": "record.start",
    "params": {}
  }
}
```

但桥接层必须立即把 `action` 转换为内部标准字段 `capability`。

### 6.1 Bridge 必须执行的动作

1. 校验 `request_id`、`device_id`、`capability` 和 `params`；
2. 检查设备已注册且在线；
3. 检查能力在设备白名单中；
4. 调用 HubService；
5. 将命令转换为现有 MQTT 格式；
6. 等待真实设备 ack；
7. 只在 ack 为 `succeeded` 时返回 `ok: true`；
8. 相同 `request_id` 重试时返回已有结果；
9. 不把 `accepted`、`queued` 或等待超时伪装成成功。

成功响应：

```json
{
  "ok": true,
  "protocol_version": "1.0",
  "request_id": "execute-20261010-0001",
  "command_id": "command-unique-id",
  "device_id": "bean_ye_1",
  "capability": "record.start",
  "state": "succeeded",
  "message": "已经开始录音",
  "result": {}
}
```

尚未完成响应：

```json
{
  "ok": false,
  "request_id": "execute-20261010-0001",
  "command_id": "command-unique-id",
  "state": "queued",
  "pending": true,
  "message": "命令已排队，等待设备执行"
}
```

## 7. MQTT 设备协议

录音豆继续使用现有 MQTT 主题，不要求本阶段改固件协议：

```text
hub/v1/devices/{device_id}/manifest
hub/v1/devices/{device_id}/availability
hub/v1/devices/{device_id}/state
hub/v1/devices/{device_id}/events
hub/v1/devices/{device_id}/commands
hub/v1/devices/{device_id}/command-acks
```

### 7.1 中枢下发命令

内部标准命令字段：

```json
{
  "type": "command",
  "command_id": "command-unique-id",
  "conversation_id": "conversation-001",
  "device_id": "bean_ye_1",
  "capability": "record.start",
  "params": {},
  "issued_at": "2026-10-10T12:00:00Z"
}
```

### 7.2 设备 ack

成功 ack：

```json
{
  "command_id": "command-unique-id",
  "state": "succeeded",
  "result": {
    "message": "已经开始录音"
  }
}
```

失败 ack：

```json
{
  "command_id": "command-unique-id",
  "state": "failed",
  "error": "TF 卡不可用"
}
```

规则：

- 设备只有在真实动作完成后才能返回 `succeeded`；
- 设备正在执行时可以先返回 `running`；
- 同一个 `command_id` 重复到达不能重复开始或停止录音；
- 重复命令应返回原结果或当前执行状态；
- 设备离线、超时和失败不能返回成功；
- ack 必须带 `command_id`，不能只带自然语言消息。

## 8. 状态统一

### 8.1 用户请求状态

上位机、随身设备和 RK3588 对外使用：

```text
received
planning
planned
awaiting_confirmation
queued
executing
succeeded
failed
timed_out
cancelled
needs_clarification
```

### 8.2 HubService 内部命令状态

HubService 可以继续使用现有状态：

```text
created
accepted
queued
running
cancel_requested
succeeded
failed
cancelled
superseded
expired
```

### 8.3 状态映射

| HubService 状态 | 对外状态 |
| --- | --- |
| `created` | `received` |
| `accepted` | `executing` |
| `queued` | `queued` |
| `running` | `executing` |
| `succeeded` | `succeeded` |
| `failed` | `failed` |
| `cancelled` | `cancelled` |
| `superseded` | `cancelled` |
| `expired` | `timed_out` |

不同层可以保留自己的内部状态，但跨层响应必须按上表转换，不能同一个词在不同层代表不同含义。

## 9. 错误码统一

```text
INVALID_REQUEST          请求字段缺失或格式错误
DUPLICATE_REQUEST        request_id 重复且请求内容不同
PLAN_NOT_FOUND           plan_id 不存在
PLAN_EXPIRED             plan_id 已过期
CONFIRMATION_REQUIRED    尚未确认，不能执行
DEVICE_NOT_FOUND         设备未注册
DEVICE_OFFLINE           设备离线
CAPABILITY_NOT_SUPPORTED 设备不支持该能力
BRIDGE_UNAVAILABLE       HTTP-MQTT Bridge 不可用
COMMAND_QUEUED           命令已排队，尚未完成
COMMAND_TIMEOUT          命令等待超时
COMMAND_FAILED           设备执行失败
MODEL_NOT_READY          模型服务未就绪
ASR_FAILED               语音识别失败
HUB_UNAVAILABLE          固定式中枢不可用
```

建议 HTTP 映射：

| 情况 | HTTP |
| --- | --- |
| 请求格式错误 | `400` 或 `422` |
| 未授权 | `401` |
| 设备或计划不存在 | `404` |
| 请求冲突或未确认 | `409` |
| Bridge/设备不可达 | `503` |
| 执行失败 | `502` |
| 等待超时 | `504` 或 `202 pending` |

## 10. 统一开发方式

### 10.1 开发顺序

所有新增设备按以下顺序开发：

1. 先定义 `device_id`、`device_type` 和能力清单；
2. 冻结 JSON 字段和状态；
3. 实现设备本地命令处理和安全校验；
4. 实现设备 manifest、availability、state 和 ack；
5. 实现 HubService 设备注册和能力校验；
6. 实现协议适配层；
7. 实现 RK3588 快速路由或智能体动作生成；
8. 先测规划，再测确认，最后才测真实执行；
9. 每一步保存 request、plan、command 和 ack 日志。

### 10.2 不允许的开发方式

- 一方使用 `action`，另一方使用 `capability`，但没有适配说明；
- 一方使用 `target_device`，另一方使用 `target_device_id`，但没有版本说明；
- 直接解析自然语言回复后发布 MQTT；
- 没有 `request_id` 就重试硬件命令；
- 把设备注册成功当成设备在线；
- 把命令已接收当成命令已完成；
- 规划阶段访问 `/command`；
- 未确认直接发送 `dispatch=true`；
- 为了测试直接改录音豆 MQTT 主题；
- 为了测试直接执行真实录音、门锁、电机或高压动作。

### 10.3 版本和变更

- 兼容性字段变更必须增加 `protocol_version`；
- 不删除已有字段，先标记 deprecated；
- 新增能力必须先更新能力清单和测试；
- 每次联调必须记录双方代码版本；
- 接口返回字段不能只靠截图说明，必须提供 JSON 示例；
- 任何协议变更都要同步更新本文件和自动化测试。

## 11. V1 验收用例

### 11.1 注册和健康

1. RK3588 `/api/health` 正常返回；
2. RK3588 `/api/hub/v1/health` 正常返回；
3. 注册 `bean_ye_1` 成功；
4. 重复注册不会重复创建设备；
5. RK3588 重启后中枢端能重新注册；
6. `base_url` 使用局域网真实地址，不使用错误的 `127.0.0.1`。

### 11.2 规划

1. “开始录音”返回 `planned` 和 `record.start`；
2. “停止录音”返回 `planned` 和 `record.stop`；
3. “查询录音状态”返回 `planned` 和 `status.read`；
4. 连续执行至少 10 次，记录耗时和路由类型；
5. 规划阶段不访问 Bridge `/command`；
6. 规划阶段不发布 MQTT；
7. 未识别目标时返回 `needs_clarification`；
8. 模型未就绪时固定指令仍能走快速路由。

### 11.3 确认和执行

1. 没有 `plan_id` 或没有确认时不能执行；
2. 只能执行已确认计划中的设备和能力；
3. Bridge 只有收到真实 `succeeded` ack 才返回成功；
4. `queued`、`running`、超时和失败不能显示“已经完成”；
5. 同一个执行 `request_id` 重试不重复发布 MQTT；
6. 同一请求 ID 改变参数时返回冲突；
7. 两条并发请求分别维护状态，不能互相覆盖。

### 11.4 异常

1. 设备离线；
2. MQTT Broker 断开；
3. Bridge 不可达；
4. 设备返回失败 ack；
5. 设备不返回 ack；
6. RK3588 重启；
7. 设备能力不支持；
8. 计划过期；
9. 重复请求 ID；
10. 无效 JSON 或缺字段。

## 12. 当前联调参数

当前环境仅用于开发联调：

| 项目 | 值 |
